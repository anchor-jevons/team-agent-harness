# 功能地图

本文件列出 `<项目名>` 面向用户的功能：有什么、用户从哪里进入、做什么、怎么验证。它像 sitemap：用户的请求或反馈含糊时（一张截图加“???”、“这个按钮不对”），先用它把请求对到具体功能；改动功能后，用条目里的验证步骤取证。

## 怎么用

- **对照请求**：在本文件中找与请求对应的条目。截图或输出片段按入口和输出格式比对，把格式相符的条目都列为候选（例如“名字 + 金额”可能来自余额，也可能来自列表）；片段与某条“证据”里的示例碰巧相同，不说明就是那一条。只对到一条时，按该条目的“验证”复现与取证；对不上，或有多条候选时，列出候选条目 ID 问用户，不猜测、不改代码。
- **改功能**：新增或改变用户可见行为的 MR，在同一 MR 中新增或更新对应条目，并在 ticket 的 `涉及功能:` 写条目 ID；reviewer 在 approve 前核对（见 `docs/agents/team.md` 的“分支与合并”）。只改内部实现、用户可见行为不变时，ticket 写 `涉及功能: none`。
- **验证**：条目的“验证”写可复制运行的命令或步骤，以及应看到的证据（输出、退出码、截图、trace）。命令只在本仓库或临时目录内运行，不访问外部地址。运行后把日期与所用提交写进“最近验证”；没有实际运行过就写 `Not verified`，不凭推测填写。

## 写法

- 每条 5–7 行，只写用户能看到或调用的功能（命令、页面、按钮、快捷键、API 端点），不写内部模块。
- ID 写 `F-<slug>`（小写字母、数字与连字符，如 `F-settle`），作为条目的三级标题，建立后不改名、不复用；功能删除时删去条目并在 MR 中说明。Ticket 与 MR 引用 ID，链接写 `docs/feature-map.md#f-settle`。
- “入口”写用户实际怎么到达：CLI 命令与参数、页面路径与点击的 DOM 元素（选择器或可见文字）、快捷键、API 方法与路径。
- Owner 写 `docs/agents/team.md` 名册中的成员 ID；没有人负责写 `None`。
- “最近验证”写 `<YYYY-MM-DD> @ <提交短 SHA>`，提交是运行验证时的 HEAD（可以是本 MR 中的提交）。

本文件与代码一起经 MR review 合入；脚本或 agent 可以提出更新，同样走 MR，不直接改目标分支。
